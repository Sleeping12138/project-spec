# 代码与安全审查

## 输入与边界

读取根 `AGENTS.md`、适用规则、相关 OpenSpec 要求、当前差异和受影响调用者。已暂存与未暂存差异、未跟踪新文件均属于可能的审查范围，以用户任务确定边界。

## 流程

1. 确定本次需求与实际差异是否匹配，查找遗漏、无关修改和兼容性变化。
2. 检查边界输入、错误传播、状态所有权、资源释放，以及改动涉及的并发、事务和重试语义。
3. 按暴露面选择安全检查：鉴权和资源归属、注入、敏感信息、Cookie 会话 CSRF、浏览器输出、外部 URL/路径处理、依赖或配置变化。纯样式变更聚焦相关交互和渲染风险。
4. 检查需求场景、失败边界与测试的对应关系。涉及支付、幂等、消息或跨服务契约时，核对必要的集成、并发/重试和恢复证据。
5. 简单改动就地审查；复杂或高风险问题可用独立子代理，交接最小上下文并明确只读/修改范围及全局约束。
6. 对发现的问题给出文件位置、具体触发条件、影响、严重程度和修复建议。没有充分依据的疑点与已确认缺陷分开。

## 输出

- 问题按影响排序：阻断/高/中/低，并给出证据；无已确认问题时明确说明审查范围和限制。
- 尚缺的测试或目标环境验证，不把审查通过等同业务验收。
- 修复问题后按相关范围复查，并使用 `project-verification` 确认结果。

审查不包含 Git 暂存、提交、自动发布或自动归档；授权遵守根入口。
