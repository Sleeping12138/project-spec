# Redis 可选规则

## 适用范围

- 仅在项目使用 Redis 时启用；先确认版本、客户端、拓扑及其承担的缓存或协调职责。
- Redis 不自动成为业务事实来源；如承载持久数据，另行明确持久化、备份与恢复目标。

## 约束

- 设计 key 时，包含业务命名空间与必要租户边界，限制长度并避免直接嵌入敏感数据。
- 写入缓存时，按业务可接受陈旧时间设置 TTL；无过期项需说明生命周期与容量责任。
- 大量 key 同时到期时，采用合理过期分散与回源保护，避免集中冲击后端。
- 更新事实数据时，定义提交后的缓存失效或更新顺序，并处理失败重试与并发回填旧值。
- 缓存未命中或 Redis 不可用时，明确降级、超时及回源并发上限。
- 允许缓存空结果时，设置适当短 TTL，避免穿透且不长期遮蔽新数据。
- 出现热 key 时，先观测访问分布，再评估请求合并、本地缓存或业务拆分及一致性代价。
- 操作大 key 或遍历数据时，控制批次与耗时；避免在请求路径执行无界全量扫描或删除。
- 配置淘汰策略时，结合数据用途与内存预算；不能假设未到 TTL 的 key 一定仍存在。
- 多步操作要求原子性时，选择事务、脚本或客户端支持的等价机制；流水线本身不保证原子性。
- 跨 key 原子操作用于集群时，确认槽位限制及 key 设计符合目标拓扑。
- 使用分布式锁时，明确锁保护范围、唯一持有者标识、租约与失效语义。
- 解锁与续期时，原子校验持有者标识后再执行，避免操作他人已重新获取的锁。
- 临界区可能超过租约时，设置可观测续期与丢锁处理；关键写入考虑 fencing token 等防陈旧写入机制。

## 验证

- 修改缓存逻辑时，验证命中、未命中、过期、淘汰、回填竞争及失效失败。
- 修改降级策略时，验证超时、断连与恢复过程中的后端负载。
- 修改原子逻辑时，验证并发交错及集群槽位约束，不仅检查单次成功结果。
- 修改锁逻辑时，验证过期后重获、旧持有者解锁、续期失败和进程暂停。
- 修改 key 或 TTL 策略时，检查内存、热 key、大 key 与过期分布的观测依据。
- 验证使用独立测试实例或隔离命名空间，清理仅限测试 key，不提供全库清空命令。
