# RocketMQ 可选规则

## 适用范围

- 仅在项目使用 RocketMQ 时启用；先确认服务端、客户端、协议及消息类型。
- 版本待项目确定；发送、重试、事务及顺序能力不预设具体版本 API 或默认参数。

## 约束

- 定义消息时，声明业务键、事件标识、事件版本与必要上下文，避免携带凭据或过量敏感数据。
- 生产端发送时，检查实际发送结果；超时可能意味着结果未知，重发必须容忍重复。
- 消费端处理时，按可能重复投递设计幂等；去重键与保留期覆盖业务重放窗口。
- 消费包含本地写入时，让去重记录与业务变更原子提交，避免先记成功后丢失业务结果。
- 业务处理完成后，才按客户端契约确认消费；失败时返回可触发相应恢复的结果。
- 设置重试时，区分瞬态与永久失败，配置次数、间隔、总耗时及毒消息处置。
- 消息进入死信队列（DLQ）时，提供告警、定位信息、责任人及审查后重放路径。
- 重放死信或历史消息时，验证幂等与事件版本兼容，避免扩大副作用。
- 数据库提交与消息发送需要一致时，选择事务消息或本地事件表等可靠方案，并说明失败窗口。
- 采用事务消息时，设计可重复执行的本地事务与确定性的状态回查；未知状态有恢复策略。
- 需要顺序处理时，声明顺序的业务范围，并按目标版本的队列或消息组机制保持路由一致。
- 顺序链路出现失败时，说明阻塞、重试与跳过策略；不承诺跨队列或全系统全局有序。
- 调整并发、批量与消费速度时，设置资源上限，并监控积压、处理延迟及失败比例。
- 服务退出或重平衡时，按客户端契约停止拉取、处理在途任务并关闭资源。

## 验证

- 修改生产或消费逻辑时，验证重复投递、发送结果未知与消费者处理中断。
- 修改幂等逻辑时，验证并发重复消息、事务回滚及去重窗口后的重放。
- 修改一致性方案时，验证数据库成功而发送失败、回查超时及恢复补发。
- 修改重试与死信策略时，在隔离环境验证耗尽路径、告警及安全重放。
- 修改顺序逻辑时，验证同一业务键的先后关系与失败恢复，避免推断跨范围顺序。
- 验证使用独立测试主题与消费组，记录目标版本和未验证能力。
